# Ten critical-review perspectives and adversarial scenarios

## Purpose and bounds

Use these perspectives to challenge implementation and interpretation at meaningful milestones. They are a development/review plan, not a claim that ten reviews have already run, not permission to spawn agents, and not authorization for unbounded external model calls.

Each review produces concrete findings, severity, evidence, corrective work and a stop/review decision. A model agreeing with another model is not independent scholarly verification. Source-processing and budget gates still apply to any external consultation.

## 1. Source editor and philological reader

Ask whether the application preserves the selected edition, canonical labels, wording, punctuation, context and authorship. Inspect long passages, ambiguous boundaries, footnotes, repeated phrases and comparison-edition differences.

Attack scenario: translator commentary is extracted between two author sentences and becomes support for a conclusion attributed to Marcus. Expected result: the import report and corpus inspector expose authorship/boundary uncertainty; processing does not approve the mixed passage automatically.

Completion evidence: reviewed import examples and exact source-resolution checks. A correct passage count alone is insufficient.

## 2. Argument and inference critic

Ask whether evidence actually bears on the proposed claim, whether premises operate jointly, and where the inferential bridge begins. Distinguish illustrations, topical similarity and support.

Attack scenario: two passages discuss mortality, but one supplies a practical reminder and another a metaphysical observation. The system merges them into an unrestricted obligation. Expected result: the bridge assumption and changed scope are challenged, with a narrowed or rejected conclusion.

Completion evidence: concise argument review against original context, not merely a valid source ID.

## 3. Historian of philosophy and contextual reader

Ask whether the reconstruction imports generic modern self-help or a preselected Stoic taxonomy. Preserve uncomfortable or unusual material and distinguish historical interpretation from modern application.

Attack scenario: a difficult statement is omitted because it contradicts the desired reassuring handbook. Expected result: it remains disputed/deferred/intentionally omitted with a reason and source identity visible.

Completion evidence: coverage ledger and explicit interpretation labels; separate cited reference corpus for historical Stoic classification where claimed.

## 4. Working writer and intended reader

Ask whether the material is concentrated, distinctive and emotionally usable rather than repetitive or vague. Compare neighboring teachings and rejected variants.

Attack scenario: the most resonant sentence introduces a universal promise that no source establishes. Expected result: it returns to meaning review or remains an unsupported variant, regardless of its clarity/resonance rating.

Completion evidence: independent fidelity, clarity and user-resonance decisions, with examples of attractive rejected wording.

## 5. Provenance and data-integrity reviewer

Ask whether every displayed arrow/color represents a stored validated relationship, whether older reviewed states are reproducible, and whether edit/invalidation propagation is complete.

Attack scenario: changing one qualifier leaves an approved green badge and colorful source gradient on dependent manuscript text. Expected result: affected assessments become stale and the earlier approved revision remains inspectable.

Completion evidence: transaction/revision tests, historical evidence snapshots and end-to-end click-through after reload.

## 6. Numerical analyst and discovery reviewer

Ask whether PCA is actually fitted, variance is measured, clustering uses the declared full-dimensional space, and the chart communicates information loss honestly.

Attack scenario: developers cluster the map’s two columns because those arrays are convenient, then call the result a hierarchy of Marcus’s ideas. Expected result: a test fails the input-space contract, and the UI refuses to mislabel the run.

Completion evidence: reproducible fitted artifacts, numerical tests and a clear distinction between computational proposals and accepted concepts.

## 7. Privacy, rights and local-boundary reviewer

Ask whether ownership, import approval, external-processing consent and sharing assumptions are kept distinct. Inspect public assets, logs, route caching and exports.

Attack scenario: a developer adds a helpful hosted synthesis endpoint that receives private passages without an explicit new consent/budget check. Expected result: the capability boundary blocks the request and surfaces the missing authorization.

Completion evidence: public/private build tests, private storage checks and export inspection. No claim that local storage alone makes inference local.

## 8. Accessibility and interaction reviewer

Ask whether the core task works without color, hover precision, a mouse or a large desktop. Inspect focus order, panes, inspectors, map alternatives and error recovery.

Attack scenario: a keyboard user focuses a highlighted clause but cannot inspect source references because the tooltip only responds to pointer hover. Expected result: the same stable inspector/list is available from focus and touch.

Completion evidence: keyboard-only workflow, plain mode, responsive screenshots and accessible map/list navigation.

## 9. Persistence, migration and operations reviewer

Ask whether old projects upgrade without losing manual work and whether jobs resume without duplicating completed results or hiding unknown outcomes.

Attack scenario: new fixtures are deployed, but existing browser projects still show the old single teaching—or a reset deletes their edits. Expected result: an explicit fixture upgrade preserves edited records, adds new examples safely and reports conflicts.

Completion evidence: old-workspace upgrade tests, restart/cancellation tests and a tested restore path.

## 10. Skeptical user and product reviewer

Ask the direct questions the current demonstration failed: where are the visible gradients, where is source tracking in the default right text, why is the content worth reading, and where is the PCA cluster map?

Attack scenario: a release note lists all the architecture pieces while the user still sees one shallow example and no discovery screen. Expected result: acceptance remains incomplete despite passing unit tests and a successful deployment.

Completion evidence: a fresh-user and upgraded-user demonstration of the requested workflow, with explicit corpus mode and no need to discover hidden features before the primary value appears.

## Review loop protocol

Choose the relevant perspectives for the increment; use all ten for major readiness reviews. Review actual artifacts and behavior, not the intention expressed in a plan. Record disagreements and prioritize correctness/boundary failures before cosmetic preferences.

Allow bounded correction and a documented recheck. Stop after repeated unresolved failures or a genuine source/consent/editorial blocker, preserving useful completed work. Do not regenerate until criticism disappears or turn a reviewer’s uncertainty into a fake consensus score.

## Sign-off record

Each perspective records inspected corpus/run/revision IDs, findings, concrete evidence, required changes, checks actually rerun and remaining uncertainty. An accepted release can retain explicitly bounded disagreements; it cannot hide them to manufacture a clean philosophical result.
