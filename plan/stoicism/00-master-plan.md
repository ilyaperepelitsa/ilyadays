# Master product and delivery plan

## Product outcome

Aurelius should make an editorial argument inspectable. A reader selects a principle, sees what it means, sees what wording expresses it, and follows every substantive assertion back through reviewed reasoning to exact source passages. The result is a concentrated book of teachings reconstructed from Meditations, with limits and tensions retained.

The application is simultaneously a source reader, an argument workbench and a writing environment. None of those functions can substitute for the other two. A beautiful paragraph without a defensible derivation is incomplete. A technically valid citation graph without intellectually worthwhile conclusions is also incomplete. A colorful cluster plot does not establish an argument.

## Immediate correction to the existing experience

The repository at the inspection baseline has five synthetic passages, one conclusion, two expression variants, two concepts and three evidence links. That is sufficient for a small provenance regression fixture, but insufficient as the main demonstration of the intended product.

The next visible increment must address four shortcomings together:

1. Source text needs clearly visible, inspectable provenance highlights, including gradients or segmented treatment where actual recorded overlap exists.
2. The default right-hand meaning pane needs source tracking directly in its text. Provenance must not be confined to an optional third pane or a separate list beneath the editor.
3. The demonstration needs several substantial, distinguishable teachings, qualifications and conflicts. More generic maxims are not a substitute for intellectual depth.
4. Discovery needs a real PCA two-dimensional view and computational cluster proposals. The plotted coordinates must come from a recorded computation, not hand placement or a decorative mock map.

Implement these with truthful corpus labeling. A synthetic mathematical demonstration can prove interactions and algorithms; it cannot be presented as analysis of Marcus or as OpenAI embeddings.

## Non-negotiable boundaries

Gregory Hays remains the selected primary translation. Robin Waterfield is optional comparison material. Do not silently replace either with a public-domain translation. An unrestricted modern text has not yet been verified as available for import. Do not purchase, scrape unauthorized full copies or remove DRM.

Import approval, external-model consent and budget authorization are three separate gates. None follows automatically from ownership, selecting a file, having a working API key, enabling a plugin or using Codex to develop the application.

The fixed embedding configuration is `text-embedding-3-large`, 3072 dimensions and cosine similarity. Do not silently shorten vectors, substitute another model or label lexical features as these embeddings. Synthetic fixtures must say what their vectors actually represent.

## Delivery tracks

### Track A — usable editorial experience

Deliver the source/meaning/optional-expression workflow, visible provenance, manual correction, revision history, locks, qualifications, challenges and honest unsupported/stale states. This track can progress with fixtures while the source file is unavailable.

### Track B — source and computational integrity

Deliver acquisition metadata, safe import, canonical segmentation, exact anchors, full-vector retrieval, reproducible projections, cluster runs and curated overlapping concepts. Its real-corpus stages depend on an authorized file and the applicable consent gates.

### Track C — reconstruction and manuscript

Deliver propositions, evidence assembly, critical synthesis, expression variants, independent ranking dimensions, coverage and navigable manuscript assembly. This track must consume reviewed source-grounded records rather than summaries of summaries.

### Track D — reliability and private operation

Deliver local persistence, migrations, resumable bounded jobs, budget reservations, recovery, accessibility, performance and rights-aware exports. A public fixture demonstration remains separate from the private research workspace.

These tracks share revision IDs and acceptance gates. They are workstreams, not permission for parallel agents or for simultaneous uncontrolled edits to shared files.

|---|---|---|---|
| R1 | Both text panes visibly explain source provenance | Stored span/target mappings and migration plan | Two-sided selection and gradient tests |

| R6 | Proposed teachings include premises, limits and critique | Proposition and evidence schemas, bounded jobs | Adversarial fidelity review and human approval |
| R7 | Expression variants preserve reviewed meaning | Clause mappings and semantic-change review | Edit/invalidation and variant-comparison checks |

R1–R3 can use a clearly labeled fixture mode. R4 is not waived by shipping R1–R3. Real-corpus R5 cannot begin just because a synthetic map has shipped.

## Definition of a substantial teaching

A teaching should identify a claim, a circumstance, a practical implication and a limit. It should distinguish itself from nearby teachings. It should remain intelligible when removed from the original sequence without pretending that every passage was originally a universal command.

A teaching about judgment, for example, must not imply that injury or injustice is imaginary. A teaching about social duty must not collapse into people-pleasing. A teaching about mortality must not delete responsibilities because time is short. These are editorial evaluation examples, not claims that the selected translation has already been analyzed.

## Default screen contract

The first viewport should show the selected teaching, at least two relevant excerpts, visible source colors on both sides, the current interpretation/review state and a route to the discovery map. A user should not need to discover a hidden expression pane before seeing provenance.

Selecting text should reveal an exact inspector. Selecting a source should reveal downstream uses. The current neighborhood should be legible without drawing every edge in the project. Plain reading must remain available with textual references intact.

## Definition of done for the project

The full project is complete only when an authorized selected corpus has been inspected, substantial conclusions have passed human review, wording preserves their meaning, a navigable manuscript retains its lineage, and unresolved material is surfaced rather than hidden.

Shipping a page, a database schema, an embedding job or a synthetic demonstration does not independently satisfy that definition. Every release note should identify its actual increment and corpus mode.

## Completion evidence and handoff

For every increment, record the touched files, schema/fixture version, source and model identities, actual commands run, screenshots or artifacts where relevant, known failures and next work package. Keep artifacts containing private source text out of tracked planning files. A later developer should be able to identify what remains blocked without asking the user to repeat the whole brief.
